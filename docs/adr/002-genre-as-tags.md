# ADR 002 — Story genre becomes its tags, with no controlled vocabulary

**Status:** Accepted · **Date:** 2026-08-06 · **Deciders:** Ashish Kr Jha

## Context

Stories can be authored by hand or generated by the LLM. `create_story` accepted
`tag_names` and resolved them into `Tag` rows. **`finalize_generated_story` did
not** — `StoryGenerateIn` had no tags field at all, so every story written
through the generator landed with zero tags.

Production had accumulated **9 stories, 0 rows in `tags`, 0 rows in
`story_tags`**. Consequences:

- no story card rendered a tag chip;
- the tag filter and `/tags` page had nothing to filter on;
- since the platform's main authoring path *is* the generator, tagging was
  effectively dead in a system that has a full tagging schema.

The generator already collects a **genre** (`horror`, `sci-fi`, `fantasy,
horror`), which is exactly the axis a reader browses by. Asking the author to
supply a genre *and* tags would be asking for the same information twice.

## Decision

**A story's genre becomes its tags**, applied in `finalize_generated_story` via
`tags_from_genre()` → `resolve_tags()`.

**No controlled vocabulary.** Names are cleaned for presentation only —
lowercased, punctuation stripped, whitespace collapsed, hyphenated — and are
otherwise stored exactly as the author wrote them. Compound genres split on
`, / & + |` and the word "and", so `"fantasy, horror"` yields two tags.

`StoryGenerateIn.tag_names` was added as an optional field; anything supplied is
merged with the genre and deduplicated after cleaning.

An earlier iteration included an alias table folding `scifi`, `sci fi` and
`science fiction` onto a canonical `science-fiction`. **It was removed
deliberately.** An alias table is a curated picklist in disguise: it silently
overrides the author's own words, and every entry is a judgement someone has to
maintain. Accepting near-duplicates is the cheaper, more honest default, and
merging them later is a data cleanup — while un-mapping a tag the system
rewrote is not recoverable.

## Why this is safe here specifically

- `tags.name` is `UNIQUE`, and `resolve_tags` is get-or-create, so cleaning
  casing and punctuation is enough to stop `"Horror"`, `"horror!"` and
  `"  horror "` becoming three rows.
- The read path already eager-loads tags (`selectinload(Story.tags)`) and
  `StoryOut.tags` was already part of the contract — the data was missing, not
  the plumbing. No API change was needed for tags to appear.
- Both authoring paths share `resolve_tags`, so a tag created by the generator
  and one typed by an author are the same row.

## Consequences

**Accepted costs**

- **Near-duplicate tags will accumulate** (`sci-fi` and `scifi` can coexist).
  This is the deliberate trade: a merge tool later, not a gatekeeper now.
- Tags are only as good as the genre field. A junk genre becomes a junk tag —
  production carries four stories tagged `test` from earlier testing.
- Genre and tags can drift apart if a story's genre is edited later; the tags
  are not re-derived on update.

**Gains**

- Every generated story is tagged and browsable with no extra author effort.
- The tag filter, `/tags`, and tag chips became functional with no UI change.
- One shared normalisation path for both authoring routes.

## Backfill

Rows predating the change were fixed by `backend/scripts/backfill_story_tags.py`
— idempotent (only touches stories with no tags), additive (inserts only), and
`--dry-run` capable. It produced 5 tags and 10 links across the 9 existing
stories.

It is a **script, not a migration**, because production runs with
`SKIP_MIGRATIONS=true`; a data migration there would silently never run.

## What the correct answer would be at scale

A **tag suggestion + merge** model: keep free-text entry, have the LLM propose
tags from the story body rather than only the genre field, surface existing tags
as autocomplete so authors converge naturally, and give moderators a merge tool
for the duplicates that still appear. That gets vocabulary convergence from
*incentive* rather than enforcement, and never overrides what the author wrote.

**Revisit when:** the tag list gets noisy enough that browsing suffers, tags
become a real navigation surface, or an author complains their tag was changed.

## Alternatives considered

| Option | Cost | Why not (now) |
|---|---|---|
| Leave the generator untagged | none | The bug being fixed. |
| Add a tags field to the generate UI | frontend work | Duplicates the genre the author already chose; and it would leave the 9 existing stories untagged. |
| Alias table onto canonical genres | small | **Built, then removed.** A picklist in disguise — it overrides the author's words and needs ongoing curation. |
| Fixed enum of allowed genres | migration | Rigid, and the generator accepts free text upstream anyway. |
| LLM-suggested tags from the body | LLM call per story | Better long-term (see above), but it adds cost and latency to generation for a problem the existing genre field already solves. |
